# 生活管家云开发迁移设计

日期：2026-10-19。状态：用户已批准设计与实施计划；本地迁移、同步实现及测试完成，远端部署与真机验收待执行。具体实现裁决见 progress.md。

## 目标与已确认事实

- 用户要求把现有生活管家代码迁入独立云开发文件夹，并让手机与 PC 小程序同步。
- 原项目：`E:/Life-Butler`；目标：`E:/Life-Butler/Life-Butler-Cloud`。
- 唯一目标环境：`YOUR_CLOUD_ENV_ID`，替代先前讨论的环境。
- 两个项目的 AppID 均为 `YOUR_WECHAT_APPID`。
- 原项目 `app.js` 只有 `App({})`；`utils/storage.js` 用同步本地缓存保存业务数据。
- 原项目图片存放于设备私有目录；直接同步这些路径不能跨设备查看照片。
- 新文件夹已有官方 quickstart 模板，`miniprogram/app.js` 的环境 ID 为空。
- 原目录不是 Git 仓库；不创建提交、不改原项目代码、不读取或修改真实设备缓存。

## 方案选择

1. 推荐：云端为业务数据主存储，在线保存成功才反馈成功；本地仅作缓存。改造范围明确，故障与冲突可见。
2. 本地优先加离线队列：离线也能编辑，但需处理队列持久化、账号切换、删除墓碑和冲突合并，首版复杂度更高。
3. 全量 JSON 覆盖上传：实现较短，但两端并发容易覆盖记录，且会遇到单文档大小限制，不采用。

首版采用方案 1。断网可查看已经加载的缓存，无法保存时明确提示失败；不将本地写入冒充同步成功。不承诺未实现的离线编辑队列。

## 迁移范围

- 将原项目的 `assets`、`components`、`custom-tab-bar`、`pages`、`utils`、应用样式、路由与 sitemap 复制到目标 `miniprogram`。
- 保留目标目录的云开发结构和 AppID，清理模板路由配置；模板示例代码可保留但不再作为首页。
- 保留待办、记账、随记、课程/考试、生活管理、专注计时、借还、菜谱/饮食、统计、搜索、个性化设置和备份恢复。
- 修改集中于启动生命周期、存储服务、云函数、媒体/备份模块、所有写入调用点与同步状态入口。页面原有业务布局保持一致。

## 身份与权限

- 使用原生 `wx.cloud.init` 连接新环境，云函数通过 `cloud.getWXContext().OPENID` 获取身份。
- 身份只信任平台上下文，不接受客户端传来的 owner/openid 作为授权依据。
- 同一 AppID 下，同一个微信账号在手机和 PC 访问同一份业务数据；不同微信账号分别保存。
- 业务集合通过云函数访问；客户端直读直写禁止，函数必须检查数据所有者并校验输入。
- 云存储采用仅创建者可读写权限，上传目录按服务端返回的用户标识划分。前端不包含腾讯云 SecretId、SecretKey 或管理员凭证。

## 数据模型与写入一致性

- 使用文档型云数据库。每条待办、账目、随记、课程、考试、生活记录、预算、专注历史、借还、菜谱和饮食安排分别保存为文档，避免把全部数据塞进单个文档。
- 文档包含所有者、业务类别、业务 ID、版本号和业务内容；设置、学期元数据、进行中的计时分别作为单例记录。
- 客户端按现有结构组装读取快照，沿用原业务校验与计算，减少不相关重写。
- 每次保存先生成相对已确认快照的变更，只提交发生变化的记录及其预期版本号。服务端事务中检查版本、验证变更后的业务数据并提交；批量转换、导入、清空和恢复保持原子语义。
- 不同记录的修改可以保留；同一记录版本不符时拒绝覆盖，保留当前编辑内容，提示刷新后重试。
- 请求携带唯一操作 ID；相同操作重试返回原结果，避免网络响应丢失导致重复添加或重复切换状态。
- 拉取支持分页；使用用户数据修订号验证分页期间没有更新，若有更新重新拉取，不能把不同版本的分页拼成快照。
- 单次请求大小、记录大小、批量数量和事务限制在代码中显式验证；超限返回清楚的错误，禁止静默截断或部分覆盖。

## 客户端生命周期与同步

- 启动时初始化云服务并拉取身份和业务快照；加载完成前显示加载状态，避免把尚未拉取的数据当成空库。
- 保留同步的内存快照供页面读取，业务写入改为异步等待云端提交。所有页面调用点必须等待保存完成后再关闭表单、清空输入或提示成功。
- 启动、返回前台、切换业务页面及用户手动同步时拉取。前台定时检查修订号并合并重复请求，后台停止轮询；定时器每秒刷新显示不触发每秒云请求。
- 云数据更新后刷新当前页面列表、统计和主题，不重置尚未提交的编辑表单。
- 显示首次加载、同步中、已同步、同步失败和最后成功时间；“我的”页面提供立即同步入口。
- 缓存按环境、AppID 和已验证用户身份隔离。身份获取失败不能进入旧用户数据，缓存写失败不能把已经成功的云端提交报告成未提交。
- 首版保证在线自动同步和手动同步；前台定时检查属于最终一致性，不宣称毫秒级实时同步。

## 照片与备份

- 新照片在提交业务记录前上传至云存储，数据库保存稳定 fileID，页面按需使用可访问的云文件地址。
- 云端提交失败，仅清理确认未被引用的新上传文件；网络结果不确定时先查操作状态，不贸然删除可能已提交的附件。
- 删除业务记录或替换图片后，只有服务端确认同一用户的所有记录不再引用时才允许清理文件。单纯拉取云数据不会触发文件删除。
- 图片预览、编辑、完整备份需兼容 cloud fileID；完整备份下载原图后嵌入，恢复先上传图片再事务提交数据，失败不破坏已有云记录。
- 云端照片下载失败要明确报错，不生成缺少照片却标为完整的备份。

## 原本地数据的迁移

- 复制源代码不会搬运手机或 PC 的真实缓存。原应用使用 `life_butler_data_v1` 存储，需要在对应设备内导出或读取才可迁移。
- 首次接入时如检测到旧缓存，先保留独立迁移备份，再显示迁移预览并由用户主动发起；不自动覆盖已有云数据。
- 支持原应用导出的完整备份。缺失本地照片要在预览中明确列出，不默认丢弃。
- 两台设备的旧数据都可导入。不同 ID 记录追加，相同 ID 且内容相同去重，相同 ID 内容不同展示冲突并要求选择；设置与学期元数据也不能无提示覆盖。
- 原有“清空”和“恢复覆盖”按钮的确认文案必须明确影响云端以及所有设备，并保持二次确认。

## 文件职责

- `miniprogram/app.js`：环境初始化、身份、启动和前后台同步。
- `miniprogram/utils/cloud.js`：环境常量、统一调用与错误分类。
- `miniprogram/utils/sync.js`：快照、修订号、并发控制、状态与页面通知。
- `miniprogram/utils/storage.js`：兼容业务接口、异步提交、旧数据迁移入口。
- `miniprogram/utils/media.js`、`backup.js`：云照片、完整备份和恢复。
- `cloudfunctions/lifeButler/`：可信身份、读写事务、幂等、数据验证与附件引用检查。
- `tests/`：同步和并发回归；原验证脚本迁入后调整路径和异步调用。
- `README.md`：环境、集合及权限配置、部署步骤、数据迁移和双端验收。

## 验证与验收

1. 对原业务规则建立回归基线，并适配异步存储验证；不接触实际微信数据。
2. 模拟两台设备的新增、修改、删除、分页、重复请求、超时后重试、断网和同条记录冲突。
3. 验证不同用户数据隔离、伪造所有者无效、无身份请求被拒绝。
4. 验证图片跨端、共享引用不误删、上传与提交失败的补偿、完整备份恢复。
5. 检查所有页面的异步错误处理与成功提示时机，以及旧数据导入去重和冲突。
6. 真机验收：手机新增，PC 同步可见；PC 修改，手机同步可见；删除和照片相同；重启保持一致；其他微信账号不可见。

## 部署边界与当前限制

- 当前没有已连接的 CloudBase 管理工具或账号凭证，环境有效性、套餐和远端部署尚未验证。
- 本地代码与离线测试完成后，需通过微信开发者工具在指定环境上传部署云函数、创建集合和设置权限，再进行双端验收。
- 不购买套餐、不改账号绑定、不删除旧环境、不代替用户执行云端清空。
- 沙箱执行工具因 MXC launcher 错误无法启动；隔离环境外的只读执行已成功，可继续本地检查。
- 测试工具问题已定位：执行进程缺少 SystemRoot/WINDIR。仅在子进程设置两者为 C:/Windows 后，使用 D:/nvm/nodejs/node.exe 成功运行原项目回归：verify.cjs 为 68 passed、0 failed，verify-life.cjs 为 35 项通过。这是原项目基线，并非新云开发代码测试结果。
